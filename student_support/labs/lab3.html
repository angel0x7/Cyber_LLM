03SYSTEM MAP

  1. Repository
  2. Checkov / Semgrep → scanner evidence
  3. Optional LLM advice · UNTRUSTED
  4. HUMAN REVIEW · accept, edit or reject
  5. Manual fix → rescan
  6. BEFORE finding → FIX + reason → AFTER status

Read it: The advice stage never applies edits. Keep the human review boundary before the repeat scan.

04WHAT TO NOTICE

Decision map

  1. ?
    Finding relevant?Inspect the rule and affected source.
  2. ◇
    Repair proposedTreat LLM advice as untrusted.
  3. ?
    Human accepts?Apply a justified manual edit, or reject it.
  4. ✓
    RescanRecord the targeted rule’s new status.

A rejected proposal returns to review. Only a human-approved edit reaches the rescan.

ENGINEER’S LENS

A scanner finding is not an exploit. Read the rule, location and context before proposing a repair.

Check this yourself before continuing.
Read the outcome labels
  • PASSNamed check passed
  • LIMITScope or measurement limit
  • BLOCKApplication control acted
  • REFUSALModel declined
  • ERRORExecution/evaluation failed
  • OFFLINELocal check or fixture
  • LIVEObserved model inference
Interpret the results

For each fix, record the scanner rule, source path, edit, reference, and after-scan status. Keep the baseline reports, after reports, a fix table, and a short reflection. A changed total alone does not prove the specific issue was fixed.
